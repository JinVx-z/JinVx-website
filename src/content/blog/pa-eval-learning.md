最近，我给自己的 Personal Agent（后面简称 PA）建立了一套很小的 Eval 集。

只有 6 个场景，围绕同一件事：让 Agent 读取我保存的项目状态，再回答“现在重点是什么”。到这篇记录写下时，这一批场景已经跑过真实模型，过程中发现的问题也完成了修复和回归。

一开始，我只是想确认这个功能到底能不能用。做着做着，我发现自己在想另一个问题：现在 Coding Agent 已经能帮我完成很多实现，那我学习开发时，最需要花精力培养的能力是什么？

这篇想从这套 Eval 为什么开始写起，也记录一下我在其中逐渐想明白的事情。

## 为什么在这里停下来写 Eval？

在[上一篇开发记录](/blog/personal-agent-first-step/)里，我花了很多篇幅思考 PA 的状态和记忆应该怎么设计。后来，我开始逐步把这些想法做出来。

做到这一阶段时，PA 已经可以保存人工确认的项目快照，Agent 也有了只读的 `get_project_state` 工具。我的预期很直接：在状态面板保存“当前重点：支付功能”，新开一个聊天，问它“现在重点是什么”，它应该读出支付功能，并告诉我这次回答使用了哪个版本的快照。

如果只看这一次演示，好像功能已经成立了。

但我很快就有了新的疑问：如果我没保存过状态呢？如果另一个项目的重点不一样呢？如果我改了状态，却继续在旧聊天里提问，它还会不会沿用之前的回答？文档和我确认的状态发生冲突时，它又该相信谁？

这些问题都会出现在我实际使用 PA 的过程中。继续往下加功能之前，我需要先知道，这一小步究竟做到了什么程度。

于是，我们先把这些预期整理成了 6 个场景。

| 场景               | 我想确认什么                               |
| ------------------ | ------------------------------------------ |
| 新会话读取状态     | 能读出已经保存的重点，并保留版本依据       |
| 尚无项目状态       | 能说明信息不足，不编造当前重点             |
| 跨项目隔离         | 回答当前项目，不把另一个项目的状态混进来   |
| 更新后新会话读取   | 新聊天能使用更新后的版本                   |
| 更新后旧会话读取   | 原来的聊天也会重新读取，不停留在旧状态     |
| 文档与人工快照冲突 | 分别说明两份依据，文档不能擅自覆盖正式状态 |

写下这些预期时，我才发现，自己已经在进一步定义 PA 的行为。比如，人工确认的快照具有怎样的地位，文档能够证明什么，Agent 能不能修改状态，这些选择都需要我先想清楚。

## 先有一个能反复运行的小工具

我们没有一开始就做很大的评测平台。第一版是一个 TypeScript 脚本，复用项目里已有的状态保存、来源读取和聊天服务。

每个场景自动准备临时项目和临时数据库，按顺序保存状态、更新状态、发起提问，结束后清理。这样不用我手动建几个演示项目，也不会把测试数据写进自己的正式项目。

完整结果保存在本地：实际保存了什么、查询前后状态有没有变化、调用了哪些工具、模型回答了什么，以及最终用了什么版本依据。模拟模型用于检查链路和确定性回归，真实模型用于观察实际回答。

这里还有一个我后来才真正理解的区分：有些事情适合交给程序断言，比如项目 ID、快照版本、状态是否被改写；有些事情则需要读回答才能判断，比如它有没有正确解释一次状态变化。

我们最初就把程序检查和回答语义复核分开记录了。但直到遇到失败案例，我才明白，这个区分到底有多重要。

## 已经读到 v2，为什么还回答 v1？

场景 05 的流程很简单：先把重点保存为“登录功能”，在同一个聊天里问一次；然后把重点改成“支付功能”，再问一次。

预期当然是第一次回答登录功能，第二次回答支付功能。

实际运行时，却出现过这样的情况：状态已经更新到 v2，应用这一轮读取的也是 v2，最终保存的快照依据同样是 v2，但回答正文仍然说当前重点是登录功能，状态没有改变。

而程序检查全部通过了。

这次失败让我开始把几个环节分开看：数据有没有正确保存？这一轮有没有重新读取？模型实际上拿到了什么？它有没有正确使用这些信息？网页最后展示的又是什么？

沿着记录往回查，我们确认保存和读取都没有出错。接下来提出的假设是：即使最新状态已经放进系统上下文，旧会话里的回答仍然可能影响模型对当前问题的判断。

修复时，我们把本轮读取的状态作为一条隐藏的上下文消息，放到当前问题附近，明确它属于这一轮。先定向复跑场景 05，再执行完整回归，观察是否有效、有没有影响其他场景。

这里还遇到过一个更细的问题：模型后来能回答支付功能了，却把上一轮关于登录功能的回答说成“当时答错了”。可上一轮对应的确实是 v1，当时的回答没有错，是状态后来更新了。

原来，“知道现在是支付功能”和“正确理解它为什么从登录变成支付”，也需要分别检查。

## 有时需要改的是应用逻辑，有时是一句话的含义

完整回归又暴露了两处问题。

一处出现在空状态场景。模型原始回答已经说明没有快照，无法判断当前重点。但应用在拿到空的来源清单后，用一条兜底提示覆盖了它，变成“暂无已确认来源，请先保存来源选择”。

这会把用户引向配置文档来源，而当前问题其实是还没有建立项目状态。问题定位到了应用最后处理回答的分支，因此修复也落在这个分支里。

另一处更小：快照的“阻碍”字段是空的，回答却说“无阻碍”。

我觉得这两个意思需要区分。空字段只能说明我没有记录阻碍，不能证明我已经确认项目不存在阻碍。对于一个希望长期理解项目的 Agent，这种小差别积累起来，就可能影响后面的判断。

我们补充了字段含义的约束，保留原始状态数据，再通过真实回答检查它是否能说清楚“未记录”。

到这里，我越来越觉得，Eval 能帮助我把原本比较模糊的“答得还行”，拆成可以具体讨论、定位和修正的问题。

## 我开始理解什么叫 Eval 驱动开发

这一轮下来，我给自己留下的流程很简单：

1. 先写清楚一个场景，以及我为什么期待这样的结果。
2. 运行并保存完整证据，默认先看指标摘要和代表性失败。
3. 每次优先处理一个主要失败类型，提出原因假设，做最小修复。
4. 先跑相关子集，确认有效，再跑完整 Eval 检查回归。
5. 简短记录问题、原因、修改、结果和剩余问题。

我也开始注意和 Coding Agent 协作时的消耗。完整日志可以留在本地，由脚本做统计，需要定位时再读取对应的内容。没有必要每一轮都把全部历史结果和无关代码重新塞进上下文。但该检查的证据、该跑的验证，仍然要做。

最后一轮完整真实模型回归，6 个场景、7 次问答，49 项程序检查通过。逐条核对回答后，前面发现的旧状态、空状态引导和空字段含义问题，在这一轮都符合了预期。

这个结果对应的是当前这一批场景。它还不能证明 PA 在任意对话里都能稳定答对。接下来真实使用暴露出新的问题，就应该继续补充评测，而不是一直只看已经通过的这 6 个案例。

## Coding Agent 越来越强，我该把注意力放在哪里？

这次经历让我重新想了一遍自己学习开发的重心。

现在我和 Codex、Claude Code 协作时，已经能把不少实现工作交给它们。这个体验越明显，我就越想知道：哪些地方需要我参与，哪些判断由我来做，产品才会更接近自己最开始想要的样子？

对于 PA，我想做出一个什么样的产品，它需要有什么基底，在项目状态和记忆上达到什么效果，这些问题始终需要我持续判断。比如这次，我希望它记住的是有依据、可确认、能区分版本的项目状态；对于不清楚的内容，我希望它能够保留不确定性，而不是替我补成一个确定结论。

这些要求如果我自己没有想清楚，就很难指望一次实现自动满足。

当然，Coding Agent 也能帮我讨论产品方向、质疑需求、发现我没想到的问题。我不想把“AI 做不到什么”当成一个永远不变的边界。对我更实际的问题是：**在当前这个开发过程中，我介入哪里，能让结果变得更好？**

这一次，我的介入就包括：不接受一次演示成功就继续加功能，追问为什么 v2 还会回答 v1，要求区分“未记录”和“没有”，以及决定这一步什么时候可以结束。

Eval 把这些判断留下来了。以后调整上下文、修改提示词或者扩展功能时，就有一组具体场景提醒我：最初希望 PA 做到的事情，有没有被新的修改破坏。

## 这也改变了我想培养的能力

所以，我现在觉得，学习开发需要同时练习两件事。

一件是把需求想清楚：服务谁，解决什么问题，哪些效果是必须达到的，哪些可以晚一点做。还要能把这些想法转成别人可以理解、程序可以检查、实际回答可以核对的预期。

另一件是具备足够的技术理解，去检查这些预期有没有落实。数据从哪里来，经过哪些函数，模型看到了什么，错误出现在哪一层，修改又可能影响哪里。如果这些都完全看不懂，即使我知道自己想要什么，也很难判断 Coding Agent 给我的修复是不是真的有效。

对我来说，这两件事需要一起培养。产品方向给技术判断提供目标，技术理解又让我有能力检查产品是否在朝那个方向走。

这套很小的 Eval 集，让我第一次比较具体地经历了这样一个过程：先说清楚想要的效果，再观察实际结果，发现偏差，找到原因，做出修改，最后重新验证。

以后 PA 还会继续增加能力。我想把这次形成的习惯带下去：每往前做一小步，都回头检查一下，它是否更接近我最开始想做的那个产品。

这也是我接下来想继续练习的开发能力。
