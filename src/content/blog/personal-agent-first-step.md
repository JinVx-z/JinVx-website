## 从文档到可信状态：我对 Agent 长期记忆的一次设计思考

> 2026-10-11 · Personal Agent 开发笔记\
> 记录当前的思考与设计决定。文中的快照、历史、抽取和 Agent 能力仍是后续计划。

我希望做一个能长期理解项目的 Personal Agent。它需要回答“现在做到哪里了”“为什么做这个决定”“下一步该做什么”，以后还要协助规划和执行任务。

开始时，我以为把项目文档交给模型，总结出进度，再保存下来，就能形成记忆。真正考虑重复读取、来源冲突和状态更新后，我发现自己需要先解决一个问题：**什么信息值得成为正式记录，又凭什么更新已有记录？**

## 1. 我的第一个疑问：每次读文档，状态会不会变？

项目目标、任务和决策往往散落在 README、开发计划、聊天和执行报告里。即使材料不变，模型也可能换一种总结方式，遗漏某个细节，或者对“基本完成”作出不同理解。

如果每次打开项目都重新抽取一次，那么“读取状态”就会同时变成“重新判断状态”。今天说已完成，明天说待验证，我很难判断究竟是项目发生了变化，还是模型的解释发生了变化。

因此，我希望把两件事分开：

- 查询时读取已经保存的正式状态，模型可以调整回答措辞。
- 更新时处理新材料，提出明确的候选变更，再决定是否应用。

可复现性的目标是让输入依据、抽取结果和确认行为可追溯；我暂时不要求模型每次输出完全相同的句子。

## 2. 我的第一个想法：能不能把来源变成几个 JSON 表？

我曾考虑按任务、修改、决策、疑问分别保存 JSON。任务有状态和时间，修改有内容和检查结果，决策有理由，疑问有待解决事项。这样机器就能直接读取字段，减少对自然语言的猜测。

这个方向保留了下来：**来源本来就有明确结构时，优先用普通程序读取、校验和映射；口述、解释和分散的自然语言材料，再交给 LLM 辅助处理。**

不过，格式和可信度需要分别判断。一个报告即使包含 `status: "done"`，仍然需要知道是谁写的、“完成”指什么、是否有检查和验收依据。结构化输出可以约束字段与类型；我据此得出的设计判断是，业务真实性还需要单独验证。[Structured outputs 官方说明](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

所以，JSON 是一种表达和交换格式，正式记录还需要身份、来源、版本与确认信息。当前也不急着把已有 Markdown 全部改成 JSON。

## 3. 记忆层级：先按职责区分，再考虑技术实现

我目前用四个概念位置理解数据流。它们帮助划清责任，具体实现可以复用同一个数据库和已有服务，不需要立即建立四套模块。

| 位置 | 保存或处理什么 | 我需要记住的边界 |
| --- | --- | --- |
| 来源材料 | 文档正文及其版本；未来可能加入 Git 证据、人工说明和执行报告 | 确认可以读取某个来源，只代表授权读取 |
| 候选变更 | 从材料中提出的字段变化、原文依据与待确认事项 | 提议尚未生效 |
| 正式业务记录 | 已确认的当前快照，以及追加的历史变化 | 状态更新有明确依据 |
| Agent 本次上下文 | 为当前问题选出的快照、相关历史和必要原文 | 按问题取用，避免每次塞入全部材料 |

其中，正式记录还有两个时间视角：当前快照回答“现在怎样”，历史回答“以前发生了什么、为何变成现在这样”。

长期决策、里程碑、过程交接和临时检查，可以先作为查询分类。等实际使用暴露出不同的保存与检索需求，再考虑更细的层级。会话日志也可以保留，但其中的推测和讨论需要经过正式写入流程，才进入项目状态或记忆。

## 4. 第二个瓶颈：文件变化，怎样影响业务状态？

我需要区分三个不同的问题：

1. 文件的时间或其他元数据变了吗？
2. 实际内容变了吗？
3. 内容里出现了需要确认的业务变化吗？

例如，我只是调整了 TODO 的排版，文件内容确实变化了，任务状态却可以完全不变。

当前决定是对实际读取的原始字节计算 SHA-256 摘要，用来识别内容版本。修改时间作为辅助信息。内容未变时，可以记录本次检查，但不自动重新抽取、不生成重复业务历史，也不推进快照版本。

来源身份和内容版本也要分开。当前可以用 `(projectId, filename)` 识别来源；同一个来源可以对应多个内容版本。业务任务则有自己的稳定 ID，标题修改后仍然是同一项任务。

还有几个容易忽略的情况：

- 内容从 A 变成 B，再回到 A，仍然发生了相对上一次成功读取的变化，但可以复用 A 的内容记录。
- 读取失败表示本次没有拿到可靠材料，应保留之前的成功版本和正式状态。
- 摘要能够识别内容，却不能还原正文。被正式记录引用的版本，需要保留正文或可追溯副本。

这一步主要由确定性程序完成，为后面的理解和确认准备稳定输入。

## 5. 从“几个 JSON 文件”走向“当前快照＋追加历史”

只保存当前状态，查询很方便，但我会丢失修改理由。只保存事件，再每次重算当前状态，又会增加现阶段的实现难度。

因此，目前选择 **SQLite 保存当前快照和追加变更历史**。JSON 用于结构化交换，JSONL 在确实需要连续事件输出或导出时使用；JSONL 每行一个 JSON 值，适合逐条处理。[JSON Lines 格式说明](https://jsonlines.org/)

这保留了我最初“事件流＋当前快照”的想法，同时将第一版收敛为可直接查询的当前状态和可追溯的历史。暂时不要求所有状态都由完整事件重放生成，也不引入完整事件溯源。

举一个设计示例：

| 时点 | 任务 ID | 当前快照 | 本次追加历史 |
| --- | --- | --- | --- |
| 开始开发 | `task-001` | 开发中 | `change-001`：进入开发 |
| 检查通过 | `task-001` | 待用户验收 | `change-002`：检查通过 |
| 用户验收 | `task-001` | 已验收 | `change-003`：用户验收 |

任务 ID 始终稳定，每次实际变化拥有独立记录。重复请求还需要操作身份或幂等约束，不能只靠标题、时间或内容摘要去重。

正式写入时，快照更新和对应历史必须放在同一个数据库事务里，应用要正确处理提交失败和回滚，避免留下只有一半的更新。SQLite 提供事务原子提交能力。[SQLite 原子提交说明](https://www.sqlite.org/atomiccommit.html)

将来恢复旧状态时，保存为一个新的版本，并记录恢复依据；中间历史继续保留。这个恢复功能针对业务记录，Git 和项目文件的恢复需要另行处理。

## 6. LLM 的位置：理解材料，提出可检查的变更

我仍然需要 LLM，因为自然语言中的目标、理由和疑问很难全部用固定规则提取。但正式状态更新需要一个清楚的入口。

计划中的主要数据流是：

```text
已确认来源
  → 受控读取正文
  → 识别内容版本
  → 结构化解析或 LLM 抽取
  → 候选变更：目标对象、字段、建议值、原文依据
  → 格式／关联／版本校验
  → 用户审查
      ├─ 拒绝／提议过期 → 保留处理记录，正式状态不变
      └─ 接受／修改后接受
          → 同一事务更新当前快照并追加历史
          → Agent 按问题查询正式记录和来源
```

候选需要关联来源版本和抽取时的快照版本。如果确认前材料或正式状态已经变化，旧提议就需要重新核对，不能直接覆盖新状态。将来重新抽取同一材料时，也应保存新的待审结果，而不是悄悄替换旧结论。

我尤其需要保留这些状态之间的区别：Agent 报告完成、检查通过、用户已验收、代码已合并。不同证据证明不同的事情，测试通过不能替代我的验收。

多个来源有冲突时，保留各自依据，标记相关字段待确认。首次实现优先采用人工确认；以后再把边界清楚、验证充分的确定性规则用于部分自动更新。

## 7. 为什么我要提前引入 Agent V0？

PA 的状态和记忆设计，最终需要通过 Agent 的实际使用来验证。如果先把底层做得很完整，再接入 Agent，我可能会花很多时间保存它并不需要的信息。

因此，我决定在来源读取和版本检测之后，就引入只读 Agent V0：

- 根据问题选择已确认的文档。
- 调用受控读取工具回答项目问题。
- 给出文件和版本依据，对缺失、冲突和不确定内容作出说明。

这时它回答的是文档中的描述，正式状态和记忆能力会继续分步加入。工具权限由应用检查，文档里的指令不能扩大读取或执行权限。

先用“目标是什么”“当前计划是什么”“某个决定依据在哪里”等真实问题，观察它需要哪些数据，再补快照、历史和记忆查询工具。

## 8. 当前决定、下一步与升级方向

截至这篇笔记写作时，项目注册、来源发现与确认已验收。当前代码已有正文读取功能，开发记录标记为“技术验证完成、待用户验收”；来源版本检测、Agent V0、快照、历史及抽取确认仍未实现。

已确定的推进顺序是：

```text
来源读取 → 版本检测 → Agent V0（只读）
→ 最小快照 → 历史查询与比较 → 结构化抽取与确认
→ Agent 记忆能力 → 执行与协作
```

下一步先完成正文读取的用户验收，再实现来源版本检测。快照阶段就要同时保存最小变更记录；后面的历史阶段主要补查询和比较，恢复能力继续拆成独立小步。

未来值得根据实际需求升级的方向包括：

- 接入 Git、执行报告和人工说明，为不同来源定义各自能证明的事实。
- 增加冲突处理、过期提示和撤销机制，并区分最近检查时间与最后业务变化时间。
- 数据增长后改善检索和上下文选择；语义索引可由正式记录生成，事实依据仍可追溯。
- 接入执行与协作后，将结果和验证证据送入同一套确认流程。
- 需要学习个人习惯时，再明确哪些偏好可长期保存、如何纠正或删除。

这些是升级方向，具体表结构、保留策略和自动化程度还要在对应阶段决定。

经过这次思考，我会从几个问题开始设计 Agent 的长期记忆：需要回答什么问题？材料从哪里来、允许读取哪些内容？对象和版本怎样关联？哪些内容是报告或推断，谁有权确认？出错后怎样追溯和修正？

这些问题能帮助我判断每一次增量是否必要，也让我在系统还很小的时候，就保留清楚的数据流与更新边界。
