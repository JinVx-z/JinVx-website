## 先找一个清楚的问题

Personal Agent 很容易变成一张不断增长的功能清单：整理文件、理解项目、安排任务、自动执行。第一步更值得回答的是：它能在什么明确场景中，帮人完成一个可以检查的小动作？这份演示把范围放在 Work / Project。输入是一个项目与一条具体请求，输出应当有依据、可阅读，并留给人决定下一步。

例如，“整理项目待办”不应直接等同于修改项目文件。可以先读取允许访问的资料，形成一份带来源的建议，再展示准备改动的内容。这样，理解和执行之间有一个看得见的边界。

### 把状态写清楚

状态不是对话的另一种叫法。对话记录表达过程，项目状态表达此刻已确认的事实。一个简单的演示模型可以是：

```ts
type TaskState =
  'proposed' | 'awaiting-confirmation' | 'running' | 'verified' | 'failed';
```

这些名字只是设计示例。真正实现时，还需要确定失败之后如何恢复、哪些动作要确认，以及证据保存在哪里。

## 完成必须有证据

| 阶段 | 要回答的问题       | 可以展示的证据     |
| ---- | ------------------ | ------------------ |
| 理解 | 这条建议从哪里来？ | 来源文件与相关片段 |
| 确认 | 将要改变什么？     | 具体差异与影响范围 |
| 执行 | 动作是否实际发生？ | 执行结果与错误信息 |
| 验证 | 结果是否满足要求？ | 检查记录与输出文件 |

“运行过命令”和“达成目标”之间可能还有很长的距离。没有报错，也不能自动说明结果正确。把验收条件提前写出来，既方便开发，也方便使用者判断是否应该继续。

## 给下一步留一点空间

小闭环的价值是可以反复理解和修改。先让一个动作走完整个过程，再考虑增加新的工具与场景。未来的真实文章可以用一次具体任务替换这里的例子，记录遇到的错误、做出的取舍和最终验证方式，让项目展示逐渐从设想变成证据。
