> 更新于 2026-10-22。当前在本地持续开发，已跑通项目资料问答和人工确认的状态保存，正在验证 Agent 能否在新旧会话中正确使用最新状态。

## 要解决的问题

每次重新打开对话，都要再解释一遍：项目做到哪了、现在重点是什么、哪些事已经确认。资料里又常常混着旧计划、Agent 的完成报告和真正验收过的结果，很难直接当成当前事实。

我想做一个能持续理解项目的个人助手。先从自己的 Work / Project 出发，让它读懂经过授权的资料，接上当前重点，并说明回答依据。更长期的方向是把自然语言目标整理成任务，在确认后交给专业编码 Agent 执行；目前先把项目上下文与状态这个基础做扎实。

## 目前已经做到什么

### 项目资料有明确的读取范围

可以注册本地项目，手动确认项目内的 `.md` / `.txt` 来源，包含子目录文件。系统按授权读取正文，以原始字节的 SHA-256 识别内容版本，保存引用所需的正文与检查记录。读取失败会保留上一次成功基线；文件变了，也不会自动被解释为项目进度变了。

### 基于 Pi SDK 的只读项目问答

已接入 Pi SDK 的模型调用与工具循环，在项目工作台中提供流式问答、本地会话保存与恢复、Markdown 展示和文档版本依据。Agent 可以列出、读取已确认来源，应用负责限制项目范围和工具权限。

### 人工确认的项目状态

当前目标、重点、阻碍和下一步可以由人确认后保存为独立快照。真实变更会在同一个数据库事务中保存新版本与前后状态记录，重复保存不增加版本，版本冲突需要重新核对。它与聊天记录、文档内容版本分别管理。这部分及前面的资料问答功能均已完成用户验收。

### 每轮读取最新状态并展示依据

每轮 Agent 问答开始前，应用都会通过 `get_project_state` 读取当前项目的最新确认快照，不依赖模型是否记得主动刷新。回答中的状态依据保留版本、确认时间与读取时间，并与文档引用分开展示；刷新页面后仍能恢复当轮依据。没有快照时明确说明，读取失败也不沿用旧会话中的状态。这一步已通过技术验证，用户验收待确认。

## 正在验证：跨会话能否接上当前重点

最小状态读取评测运行器已实现，覆盖 6 个合成场景：正确状态、尚无状态、项目隔离、更新后新会话读取、更新后旧会话读取，以及文档与人工快照冲突。每例使用独立临时项目和数据库，记录实际工具访问、回答、状态版本及查询前后的数据。

首轮真实模型执行共 7 次查询，快照侧的程序检查全部通过，查询前后正式状态与历史未改变。另有仅开放文档工具的对照，用来明确它无法直接读取正式快照的能力边界。

**程序检查通过还不等于回答语义全部正确。** 首轮阅读发现：状态更新后，Agent 虽然读到了新重点，却把旧版本下原本正确的回答称为错误。时间解释仍需修正，最终人工语义复核和运行器的用户验收也待完成；目前不把这些结果写成整体正确率。

## 我在坚持的边界

- 文档、Agent 报告和人工确认的状态具有不同性质；报告不能自动覆盖正式状态。
- Agent 当前只读，不能写文件、执行命令或修改正式状态。
- 来源版本、业务状态版本和聊天记录分开保存，回答应能追溯到当时实际读取的依据。
- 检查通过、用户验收、代码提交与合并分别记录，避免把“Agent 说完成了”当成最终结论。

自动抽取与确认候选、历史浏览与恢复、任务卡、本地 Runner 和编码执行器接入都还未实现。通用网页检索及生活助手也仍是后续方向。

## 技术与开发方式

界面使用 Next.js、React 和 TypeScript；本地业务数据由 SQLite 与 Drizzle 管理；Pi SDK 负责 Agent 会话、模型调用和工具循环，应用层负责授权与业务校验。采用小步开发，每完成一个可运行的闭环，就验证实现、亲自验收并梳理调用链，再推进下一步。

## 下一步

先处理首轮评测暴露的时间解释问题，完成状态读取与评测结果的复核和验收。之后再逐步探索“用户表达 → 候选变化 → 人工确认 → 保存 → 新会话读取”的最小记忆更新闭环。
