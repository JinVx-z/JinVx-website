在我刚开始学习agent开发时，急需一个项目让我大致明白：如果要做出一个能用的agent产品，需要完成哪些链路的联通，各环节是这么协调的，需要拥有什么技术栈等等，只有当你真正自己动手去做了，才知道你缺什么，实际开发中真正要注意的环节是哪些。因此我没有把这个引我入门的小项目立的太大：就是简单复现一个 Research Agent。Agent 核心没有用现成框架，而是用 OpenAI 兼容 SDK，加上自己写的调度代码搭起来的。

最初，它有三样东西：一个本地小向量库作为知识库，一个 Web Search 工具，还有一个我当时觉得最关键的部分——Router 决策层。

项目做完后回头看，我才发现：自己以为在设计路由，实际上已经在做上下文工程。

## 分类准确，为什么还是不够用？

Router 的工作很直接：拿到问题，判断它属于哪一类，再送到三条路径之一。

- **Direct**：不检索，直接回答。
- **Search**：联网搜索，再根据结果回答。
- **Knowledge**：检索知识库，再结合资料回答。

每条路径都有自己的提示词和处理逻辑。简单问题不需要进入多步循环，调用链短，成本也比较可控。

我当时以为，只要分类分得准，这个 Agent 就成立了。

然后我撞墙了。

它能处理简单、单一的问题，但遇到需要同时使用知识库和联网搜索的问题，比如“这个库的最新版是不是改了文档里描述的行为”，单次路由就不够用了。它只能选一条路，不能在同一次任务里先查已有资料，再核对最新信息。

问题已经超出了“三选一”的能力边界。

## 加上循环，工具才真正串了起来

后来，我给它加了一个 ReAct 循环：模型根据当前信息决定下一步行动，调用工具，读到结果后，再决定继续查还是给出答案。

这样，知识库和联网搜索就能串起来：先查库，再联网，最后综合。

为了控制成本，我把循环预算设为最多五步，并在预算用尽时强制收尾。五这个数字没有什么特殊道理，只是当前项目里的一个取舍。

但有一件事很明确：没有边界的循环会绕圈，时间和钱会一起消耗。**步数上限是设计的一部分。**

循环解决了“能不能连续使用工具”的问题，却没有自动解决“拿到信息后能不能答好”的问题。

## 真正影响答案的，是模型手里有什么

盯着这个 Agent 想了一会儿，我发现，真正的收获和多加了几个功能关系不大。

答案质量不只取决于 Router 分类准不准，也不只取决于循环能跑几步，还取决于三件更底层的事：

1. 数据从哪里来，又流向哪里。
2. 这些数据交给哪一步、哪个角色处理。
3. 到达模型时，哪些内容被保留，又以什么形式和顺序出现。

同一个问题、同一批检索结果，只是取舍和顺序不同，答案就可能差出一截。

检索到十条结果，是全部塞进去，还是挑出三条最相关的？哪些需要保留原文，哪些可以折成摘要？历史对话要留多少？工具结果太长时，从哪里截断？

这些选择都会改变模型作答的条件。它也未必会主动告诉我：是资料不够，还是噪声太多。

所以，我给自己记下了一句：

> 对我这个项目来说，Agent 设计的核心，是把每次调用的上下文组织好。路由和工具编排，也要围绕这件事来设计。

Router 决定从哪里开始；到了那条路径上，模型手里有什么，才决定它能怎么回答。

回头看，我为三条路径分别编写提示词、组织检索结果、约束引用方式，其实已经在处理上下文了。只是当时，我把注意力都放在了“分类”上。

## 从“走哪条路”到“每次给模型看什么”

现在，我更愿意用“一份状态，加一个编译函数”来理解 Agent。

这里的“编译”是一个比喻：把问题、历史对话、检索结果和当前任务进度，按这一轮的角色与任务裁成一份上下文，再交给模型。它还只是我对设计方式的理解，不代表项目已经有了完整的状态管理系统。

分类路由可以看作这种组织方式的一个简单起点；多步循环则要求我在每一轮重新判断，该保留什么、补充什么，以及什么时候停下来。

这条路我还没走远，但至少开始知道该往哪里检查了。

如果继续迭代这个 Agent，我会先把一个问题写清楚：**每次调用，究竟给模型看什么？**

功能可以继续加，但我想先让每一轮上下文的来源、取舍和边界都说得清楚。
